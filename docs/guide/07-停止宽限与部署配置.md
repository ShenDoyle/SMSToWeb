# Node 自托管：停止宽限配置（部署者必做）

> 本篇**只适用于 Node / Docker 自托管**。用 Cloudflare / Vercel / Netlify / Deno / EdgeOne 的用户**不需要**看这一篇。
> 一句话：**把你部署方式的「停止宽限」设成 90 秒**，否则重启或升级时，正在发通知的后台任务会被直接杀掉。

---

按你**实际使用**的部署方式，从下面四节里**挑一节照做**，不需要四种全配：

## 二、四种配置，只做对应的一种

### 2.1 `docker run`

在启动命令里加 `--stop-timeout=90`：

```bash
docker run -d --name smstoweb --restart unless-stopped --stop-timeout=90 -p 8787:8787 \
  -e RECEIVE_TOKEN=你的密钥 \
  -e TURSO_DATABASE_URL=libsql://xxx.turso.io \
  -e TURSO_AUTH_TOKEN=你的令牌 \
  smstoweb
```

- **在哪改**：你启动容器的那条命令（第一次创建容器时就带上；已存在的容器需要删除重建，或用 `docker update --stop-timeout=90 smstoweb` 后确认生效）。
- **完成标志**：`docker inspect smstoweb --format '{{.Config.StopTimeout}}'` 输出 `90`。

### 2.2 `docker stop`

每次停止时带 `--timeout 90`：

```bash
docker stop --timeout 90 smstoweb
```

- **在哪改**：你的停止脚本 / 运维手册 / CI 里的停止步骤。
- **注意**：`docker stop` 的超时是**临时**的，只对这一次生效；如果别的地方（如编排工具）也会停容器，仍要按 2.1 / 2.3 设置持久值。
- **完成标志**：停止耗时明显超过 10 秒且容器退出码为 `0`（不是 `137`）。退出码 `137` 表示被 SIGKILL 强杀，说明宽限没生效。

### 2.3 Docker Compose

在**你的** `compose.yaml` 的该服务下加一行：

```yaml
services:
  smstoweb:
    image: smstoweb
    stop_grace_period: 90s        # ← 加这一行
    ports:
      - "8787:8787"
    environment:
      RECEIVE_TOKEN: ${RECEIVE_TOKEN}
    volumes:
      - sms-data:/data            # 本地 SQLite 模式时用于持久化
volumes:
  sms-data:
```

- **在哪改**：你自己服务器上的 `compose.yaml`。仓库里**没有**生产 Compose 文件，本轮也**没有**替你创建或改动任何生产编排文件；[compose.example.yaml](../deploy-templates/compose.example.yaml) 只是可复制的示例模板。
- **完成标志**：`docker compose config | grep stop_grace_period` 显示 `90s`；重启后容器日志出现 `shutdown_grace=80s`。

### 2.4 systemd

在**你的** `.service` 文件的 `[Service]` 段加一行：

```ini
[Service]
ExecStart=/usr/bin/node /opt/smstoweb/server.mjs
TimeoutStopSec=90s                # ← 加这一行
Restart=on-failure
```

```bash
sudo systemctl daemon-reload
sudo systemctl restart smstoweb
systemctl show smstoweb -p TimeoutStopUSec    # 应显示 1min 30s
```

- **在哪改**：`/etc/systemd/system/smstoweb.service`（你自己的服务器）。[smstoweb.service.example](../deploy-templates/smstoweb.service.example) 是示例模板，不会自动生效。

### 2.5 Fly.io / Railway 等 PaaS（未验证）

这些平台由平台自己管理进程停机。本轮**没有在官方文档中核实**能否把它们等价的停机宽限设为 90 秒，因此**不提供配置示例，也不承诺可用**。

请先查阅该平台当前文档；如果无法设置，请明确接受这个后果：**在重启/重新部署时，尚未发完的后台通知可能丢失**（消息本身已入库，不会丢，丢的是转发通知）。

## 三、时间预算关系（为什么是 90 秒）

四层预算必须从小到大、层层留余量，不允许「容器先杀进程、应用还没等完」：

| 层 | 名称 | 默认值 | 由谁决定 | 推导依据 |
|---|---|---|---|---|
| ① | **HTTP 在途请求等待** | **30s** | 项目自动 | 长轮询 `WAIT_MAX_SECONDS` 3–25s（默认 25s）+ 5s 响应写出余量；`server.close` 要等全部在途请求结束 |
| ② | **后台任务 drain 等待** | **45s** | 项目自动 | 单渠道 10s 超时 × 最多 4 次串行重试（40s）+ 5s；多目标/多渠道是**并行**取最大值，不相乘 |
| ③ | **应用整体停机宽限** | **80s** = ①+②+5s | 项目自动，可调大 | `SHUTDOWN_GRACE_MS`：可调到 `120000`，但**禁止低于 80000**（设小了会被忽略） |
| ④ | **容器 / 服务停止宽限** | **≥90s** = ③+10s | **必须由你（部署者）设置** | 本文 §2 的四种配置 |

关系：**① + ② + 5s = ③ ≤ ④ − 10s**。Docker 默认停止宽限只有 **10 秒**，远小于 ③，会先发 SIGKILL，把整套等待机制直接抵消。

> `Dockerfile` 里的注释**只能说明**这个要求，**不能设置**容器宽限；`STOPSIGNAL` 只能改信号类型、不能改宽限。这是 Docker / systemd 层面的配置，不属于应用代码。

## 四、哪些是项目自动完成的，哪些必须你做

| 事项 | 谁负责 | 说明 |
|---|---|---|
| 推导 80s 应用宽限、登记并等待后台任务 | ✅ 项目自动 | `platforms/node/lifecycle.mjs` + `server.mjs`（M-1 修复） |
| 停机时拒绝新请求（503）、等待在途 HTTP | ✅ 项目自动 | `server.close` + draining 状态 |
| 后台任务超时记 `background_task_timeout` / `background_tasks_unfinished` | ✅ 项目自动 | 超时**不记为成功**、不静默丢弃 |
| 任务收敛后才关闭 SQLite、再 `exit(0)` | ✅ 项目自动 | `process.exit` 永远在数据库关闭之后 |
| **把容器/服务停止宽限设为 ≥90s** | ❌ **必须你做** | §2 四选一；项目无法代劳 |
| 填 `RECEIVE_TOKEN` 等密钥、准备数据库、域名与 HTTPS | ❌ 必须你做 | 见 [Node 自托管指南](03-平台部署/06-Node自托管.md) |
| 备份 SQLite 文件 / 数据库 | ❌ 必须你做 | 见 [更新与维护](09-更新与维护.md) |

## 五、怎么确认配置生效

1. 启动容器，看日志里有没有 `shutdown_grace=80s`：
   ```bash
   docker logs smstoweb 2>&1 | grep shutdown_grace
   ```
2. 确认你的部署方式那一层的宽限 ≥90s（§2 各节的「完成标志」）。
3. 做一次真实停机演练：在有一条长轮询/后台通知在跑的时候执行停止，观察容器退出码是 **`0`** 而不是 `137`，日志依次出现 `received SIGTERM` → `shutdown_started` → `http_drained` → 后台任务完成 → `local sqlite closed` → `shutdown_complete`。

## 六、本地验证 ≠ 生产已配置（重要区分）

| 类型 | 结论 |
|---|---|
| **本地验证（已完成）** | 在 **WSL2 Ubuntu + Docker** 用真实 `docker stop` 信号做过 5 组组合验证：正常完成（25s 长轮询完整返回 + Webhook 真实送达 189 bytes）、SIGTERM 后后台任务仍能真实读取 SQLite、任务超时有明确记录且不报成功、3 个并发任务全部完成后才关库、兜底路径强制退出。原始日志与退出码在仓库外 `M1-fix/`。 |

## 七、已知边界（不夸大）

- 后台通知任务**没有任务级统一截止时间**，有界性完全由 45s drain 提供；未来若调整渠道超时或重试次数，需要重新核算本表。
- 超时任务**不取消、不补偿**：消息已经入库不会丢，但那条转发通知**可能遗漏**。日志会明确记录，不会伪装成功。
- Turso 模式下数据库读取没有超时上限；本地 SQLite 模式由 `LocalDatabase.close()` 做 fail-fast，关闭后访问会报错而不是静默降级。
- Fly.io / Railway 等 PaaS 的等价宽限**未核实**，见 §2.5。
