# 部署与使用验收场景（6 类用户）

> 目的：**不能只证明开发者可以部署成功**。每个场景都写清起点、操作、哪些能自动化、哪些必须用户做、成功判据、出错怎么恢复。
> 本轮为**文档路径验收**（依据现有文档、源码与本地证据逐项核对），**不是六类真人在六个平台上的实测**；涉及真实平台部署的部分明确标注为「未实测」。

## 场景 1：第一次接触项目的普通用户

- **从哪里开始**：[用户文档首页](README.md) → [项目介绍](01-项目介绍.md)。先知道「能干什么、要准备什么、要不要花钱」。
- **要执行哪些操作**：选平台 → [快速开始](02-快速开始.md) → 对应[平台指南](03-平台部署/README.md) → 填凭据 → 发第一条测试消息。
- **可以自动化**：部署按钮把代码变成应用；`ensureSchema` 首次请求自动建表；页面自动刷新。
- **必须用户完成**：注册平台与 GitHub 账号、生成并填 `RECEIVE_TOKEN`（开启登录再加 2 项）、发送测试消息。
- **如何判断成功**：管理页出现测试消息；页脚显示版本号。
- **出错恢复**：[常见问题](05-常见问题.md) 按现象查；部署失败、收不到消息各有独立排查表。
- **⚠ 未解决的缺口**：当前版本**网页里没有「发一条测试消息」按钮**，第 4 步必须用手机转发端或一条 `curl` 命令。这对完全不懂命令行的用户仍是门槛。已列为 [界面问题清单](08-界面交互问题清单.md) 的 **B-6**（新增数据写入接口，属权限/数据操作，本轮禁止实施）。

## 场景 2：没有开发经验、但有平台账户

- **从哪里开始**：[快速开始](02-快速开始.md) 路线 A（Cloudflare）。
- **要执行哪些操作**：点按钮 → 授权 → 设置页填 `RECEIVE_TOKEN`（+ 登录相关 2 项）→ 打开页面 → 发测试消息。
- **可以自动化**：创建并绑定 D1 数据库、配置 CI、自动建表、自动刷新。
- **必须用户完成**：3–4 个字段；**按钮不会替你填密钥**。
- **如何判断成功**：页面出现消息；开启登录时能用自己设的密码登录。
- **出错恢复**：`workers.dev` 的 UA 检查（error 1010）→ 带描述性 `User-Agent` 或绑自定义域名；密码问题 → 回平台环境变量检查 `ADMIN_PASSWORD` / `SESSION_SECRET`。
- **文档已做的适配**：所有字段给了示例值与「去哪里拿」；术语统一放在[快速开始](02-快速开始.md)末尾的「名词解释」；不要求理解 API/数据库。

## 场景 3：已经有服务器、希望自行部署

- **从哪里开始**：[Node 自托管指南](03-平台部署/06-Node自托管.md) → **[停止宽限与部署配置](07-停止宽限与部署配置.md)（第零步）**。
- **要执行哪些操作**：设宽限 → 准备代码/镜像 → 选 SQLite 或 Turso → 填环境变量 → 启动 → 反代/HTTPS。
- **可以自动化**：应用自动建表；停机时自动登记并等待后台任务、超时记日志、任务收敛后才关 SQLite。
- **必须用户完成**：**≥90s 停止宽限**、密钥、数据卷、端口、域名/TLS、备份。
- **如何判断成功**：启动日志 `shutdown_grace=80s`；停机演练退出码 **0**（不是 137）；页面出现测试消息。
- **出错恢复**：退出码 137 → 回[宽限配置](07-停止宽限与部署配置.md)核对；`node:sqlite` 报错 → 换 Node 22.13+；数据丢失 → 检查 `-v` 卷。
- **验证性质**：本地 WSL2 Docker 五场景已实测（`M1-fix/`），**生产配置未落地、本轮未创建任何生产编排文件**；Fly.io / Railway 的等价宽限**未核实**。

## 场景 4：从旧版本升级

- **从哪里开始**：[更新与维护](09-更新与维护.md) / [升级指南](../UPGRADE.md) 第七节。
- **要执行哪些操作**：Git 平台点 **Sync fork**（或重新 build 镜像）→ 等自动部署 → 看页脚版本 → 收一条测试短信。
- **可以自动化**：`ensureSchema` 自动建表/补列/建索引（幂等、失败不阻断主流程）；旧环境变量自动兜底。
- **必须用户完成**：触发重新部署；**Node 用户升级前必须先配好 ≥90s 宽限**，否则重启会丢后台通知；确认 `RECEIVE_TOKEN` 仍在。
- **如何判断成功**：页脚版本更新、历史消息还在、推送端**无需改动**。
- **出错恢复**：页面无数据 → 手动执行 `schema.sql`（幂等）；收不到 → 检查 `DISABLE_RECEIVE_TOKEN`；要回退 → 重新部署旧代码，只要 `RECEIVE_TOKEN` 还在就安全。

## 场景 5：部署后第一次收不到消息

- **从哪里开始**：[常见问题 · 收不到消息](05-常见问题.md#收不到消息) 的 8 步排查表。
- **要执行哪些操作**：依次核对地址、token、手机后台、发送日志、去重、筛选条件、库结构、429/401。
- **可以自动化**：重复消息自动去重；长轮询失败自动指数退避；库结构自动自愈。
- **必须用户完成**：按表逐项检查并修正推送端配置。
- **如何判断成功**：页面出现消息，且能说出是哪一步出了错。
- **出错恢复**：文档对 401/403、429、去重、自愈失败都给了明确下一步；`duplicated:true` 明确标注为**正常行为**，避免用户误判故障。
- **⚠ 已知界面缺口**：筛选无结果时，界面目前只有「没有符合条件的消息」一句，**没有清筛选/查时间范围/去发测试通知的引导**（[界面问题清单](08-界面交互问题清单.md) 5.1）。本轮已把排查路径写进 FAQ 作为补偿，界面修订待批准。

## 场景 6：希望更换部署平台

- **从哪里开始**：[常见问题 · 更换部署平台](05-常见问题.md#更换部署平台)。
- **要执行哪些操作**：新平台部署 → 迁移数据 → 改所有推送端域名 → 并行观察 → 停用旧平台。
- **可以自动化**：六平台接口路径、鉴权逻辑、数据格式一致；`ensureSchema` 在新库自动建表。
- **必须用户完成**：新平台账号与数据库、数据导出/导入、推送端地址更新、通知渠道凭据重新配置。
- **如何判断成功**：新平台能收到消息，旧平台停用后无异常。
- **出错恢复**：CSV/JSON 只含消息内容，**不含设备/令牌/设置**，这些要在新平台重新配置；文档已明确标注，避免误以为能一键还原整站。

## 本轮验收的总体结论与未覆盖项

| 项 | 结论 |
|---|---|
| 文档路径完整性 | 6 类场景都有明确起点、操作、成功判据、恢复路径；**没有出现「只有开发者能走通」的隐含步骤**（所有技术步骤都给了入口与示例） |
| 硬缺口 | 场景 1/2 的「网页内发测试消息」按钮缺失（B-6）；场景 5 的空状态排错引导缺失（5.1）；场景 3 的宽限配置必须由部署者执行 |
| 未实测 | 六类**真人**在六个平台上的真实部署；五个 Serverless 平台的真实部署；真机浏览器矩阵 |
| 本地实测 | 850 项自动化测试；Node 停机五场景真实 Docker 验证（WSL2）；文档链接与源码一致性脚本核验（见 `M2-M3-docs/raw/`） |
| 不能声称 | 「普通用户已在所有平台验证成功」「生产环境已配置停止宽限」「一键部署已完成全部配置」 |
