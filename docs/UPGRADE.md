# 升级指南（存量用户必读）

> 适用：从任意旧版本升级到 **v1.0.4**（浏览器独立会话时长）。
> 一句话结论：**绝大多数用户只需要「更新代码 + 重新部署」，其余什么都不用做。**

---

## 一、两类升级，你属于哪一类？

| 类型 | 触发条件 | 你要做的事 |
|---|---|---|
| **A. 代码更新型**（绝大多数） | 只是换了新版本代码，数据库没动过结构 | 重新部署/替换代码即可。**首次请求会自动补齐库结构，无需任何手动操作** |
| **B. 库结构升级型** | 你的库是老版本建的（没有 `tokens` 表） | 同上——新代码内置运行时自愈（`ensureSchema`），**首次请求自动建表/补列/建索引**。只有自愈失败（极少数平台异常）才需要手动执行 SQL，见第三节 |

本次升级新增的库结构只有一项：**`tokens` 表**（多命名接入令牌，存 SHA-256 哈希）+ 3 个索引。其余（`devices`、`messages` 及各列）结构不变。

> **v1.0.1 追加**：`tokens` 表新增 `expires_at`（有效期）与 `note`（备注）两列——已按上述流程升级过的库**无需任何操作**，新代码首请求会自动补列（与建表同一套自愈机制）；新库直接建齐 9 列。

> **v1.0.2 追加**：新增 `settings` 表（服务端键值设置，当前仅存会话时长 `session_ttl_minutes`）——同样**无需任何操作**，新代码首请求自动建表；设置缺失时登录回退默认 30 分钟。

> **v1.0.3 追加（重要，但依然零操作）**：`settings` 表开始承载**通知渠道配置**（11 个渠道的 Webhook/Token/密钥、渠道启停、转发类型、重试次数、跳转链接）与**高频业务参数**（保留天数、号码归属地开关/接口）。
>
> - **不新增表、不新增列、不新增索引**：只向既有 `settings` 表写键，旧库无需执行任何 SQL。
> - **旧环境变量继续有效**：数据库里没有对应键时，仍按旧环境变量读取；数据库有值时数据库优先。升级后不配置任何东西，行为与升级前完全一致。
> - **登录密码 `ADMIN_PASSWORD` 与会话签名密钥 `SESSION_SECRET` 仍然只走环境变量**，本次没有把它们搬进数据库，也没有新增任何环境变量。
> - 想把旧环境变量搬进数据库：管理页 → 设置 → 通知设置 → **「从环境变量导入」**（只导入数据库缺失的键，不覆盖已有值）。
> - 保留键 `schema_meta`（结构指纹）与 `settings_rev`（并发修订号）由新代码自动维护，设置接口拒绝写入/删除，**不要手工改**。

> **v1.0.4 追加（零操作）**：会话时长升级为**浏览器独立**——管理页「会话时长」面板改为读写浏览器本地配置（localStorage，键 `sms_ttl_min`），登录时随请求声明，服务端校验 5~43200 后按其签发独立 exp。
>
> - **不新增表、不新增列、不新增环境变量**：`settings` 表的 `session_ttl_minutes` 保留，降级为**全局默认值/兼容回退**（登录请求未声明时使用，老版本客户端行为不变）。
> - 改一个浏览器的时长不影响其他浏览器；已签发会话的过期时间签发时确定，不会被延长或缩短。
> - 未设置浏览器本地配置时，登录按全局默认签发——与 v1.0.2/v1.0.3 行为完全一致，升级后无感。
>
> **v1.0.4 追加（UI 与 API 扩展，依然零操作）**：设置中心重构（分组 + 作用域徽章 + 未保存确认）、全项目 Design System、消息列表改为「默认 10 条 / 两行摘要（≤120 码位）/ 加载更多 / 未读入口」。
>
> - **不新增表、不新增列、不新增索引、不新增环境变量**：消息列表的游标分页、摘要瘦身（`slim=1`）与单条详情接口均为**接口层扩展**，不改存储结构。
> - **旧调用方不受影响**：不传 `slim` / `cursor` 时，列表仍返回完整正文并按 `page` 分页；默认每页条数由 20 改为 10 仅影响未显式传 `limit` 的调用。
> - 新增 `GET /api/messages/{id}`（单条完整消息）与 `409 CURSOR_STALE`（分页会话期间星标集合变化时拒绝过期游标，前端自动回到首屏）。
> - 设置页入口统一为「右上角 ⚙ 设置」直接打开设置中心；原设置下拉菜单已移除（统计在右侧栏、令牌在「安全」分组）。
>
> **v1.0.4 后续（未发版，前端与接口扩展，依然零操作）**：管理页前端替换为 1180px 仪表盘（左列表 + 右设备/设置概览/快捷统计）；多选改为右键/长按进入；验证码移到卡片顶部右侧（主色胶囊 + 一键复制，失败明确报错）；设置中心新增界面语言、分页、本浏览器偏好（消息开关 + 免打扰）；通知支持每渠道多目标（`notify.targets`）；接入令牌支持重命名（`POST /api/tokens/rename`）；列表/导出新增 `read=1` 筛选。
>
> - **不新增表、不新增列、不新增环境变量**：`notify.targets` 与设置项同样存放在现有 `settings` 键值表；令牌重命名只更新 `tokens.name`。
> - 旧接口全部保持兼容；`notify.targets` 为空时回退原单目标配置与旧环境变量。

## 二、升级后你需要做什么 / 不需要做什么

### ✅ 需要（仅一条）

1. **确认数据库绑定/环境变量没变**：部署平台上的 D1 绑定（Cloudflare）或 `TURSO_DATABASE_URL` / `TURSO_AUTH_TOKEN`（其余平台）保持原样即可，不需要新建库。

### ❌ 不需要

- **不需要**重新配置 `RECEIVE_TOKEN`（环境变量令牌照常工作，库内令牌与它并存，库内优先）；
- **不需要**改动推送端（SmsForwarder 等客户端的 URL、token、脚本全部原样可用）；
- **不需要**手动执行任何 SQL（六平台均已确认支持自动自愈，见下方矩阵）；
- **不需要**立刻创建命名令牌——这是**可选**的后续动作，详见第四节；
- **不需要**修改通知相关环境变量（`FEISHU_WEBHOOK` 等）：没有数据库键时它们照常生效；只有你主动在设置页保存/导入后，数据库值才会覆盖同名变量。

### 六平台自愈能力矩阵

| 平台 | 数据库 | 建表 | 补列 | 建索引 | 结论 |
|---|---|---|---|---|---|
| Cloudflare Workers | D1 | ✅ `CREATE TABLE IF NOT EXISTS` | ✅ `PRAGMA table_info`（官方兼容清单内）+ `ALTER TABLE ADD COLUMN` | ✅ | 全自动，无需手动 |
| Vercel | Turso（libsql HTTP v2） | ✅ 官方 `execute` 即支持 DDL | ✅ 同左 | ✅ | 全自动，无需手动 |
| Netlify | Turso（libsql HTTP v2） | ✅ | ✅ | ✅ | 全自动，无需手动 |
| Deno Deploy | Turso（libsql HTTP v2） | ✅ | ✅ | ✅ | 全自动，无需手动 |
| EdgeOne Pages | Turso（libsql HTTP v2） | ✅ | ✅ | ✅ | 全自动，无需手动 |
| Node / Docker 自托管 | node:sqlite（SQLITE_PATH）或 Turso | ✅ 首次启动自动执行 schema.sql | ✅ | ✅ | 全自动（本项目测试即此路径，已实证） |

自愈机制：幂等（重复执行无副作用）、失败不阻断主流程（仅告警，下次请求自动重试）、每个库实例只完整跑一次。

## 三、升级后自检（30 秒）

1. **看后台**：管理页 → 设置 → 「统计」弹窗，底部有一行 **「库结构自愈：正常（时间）」**——看到「正常」即升级成功。若显示「失败：原因」，原因摘要会直接给出（常见为数据库令牌过期/绑定丢失）。
2. **收一条测试短信**：推送端发一条消息，管理页能看到 → 链路完整。

### 自愈失败时的手动兜底（仅以上矩阵全部失败时才需要）

自愈失败会自动重试，一般无需干预。若确认需要手动建表（例如库权限被平台策略收紧）：

- **Cloudflare D1**：
  ```bash
  npx wrangler d1 execute <你的数据库名> --remote --file=platforms/cloudflare/schema.sql
  ```
- **Turso（Vercel / Netlify / Deno / EdgeOne）**：
  ```bash
  turso db shell <你的数据库名> < platforms/cloudflare/schema.sql
  ```
- **Node 自托管（SQLITE_PATH）**：删除进程后重启即可（启动时自动执行 schema.sql）；或用任意 sqlite3 CLI 执行 `schema.sql`。

`schema.sql` 幂等（全部 `IF NOT EXISTS`），重复执行安全。

## 四、升级后可选：切换到命名令牌（推荐，非必须）

1. 管理页 → 设置 → **「接入令牌」** → 新建令牌（如 `phone-main`），**明文只显示一次，立即复制**；
2. 把推送端配置里的 token 换成新令牌（推荐用 `X-Receive-Token` 请求头，`?token=` 仅兼容）；
3. 确认新令牌收发正常后，可设置环境变量 `DISABLE_RECEIVE_TOKEN="true"` 停用引导令牌——此后**只有库内命名令牌可用**，单个设备泄露可秒级吊销/轮换。

不执行第 3 步也完全安全：环境变量令牌与库内令牌并存，行为与旧版一致。

---

## 五、回退路径

升级后如需退回旧版本：

1. **代码回退**：重新部署旧版本代码即可。旧版只认识 `RECEIVE_TOKEN` 环境变量——只要它还在（本升级从未删除或改动它），回退后推送立即恢复。
2. **库结构无需回退**：`tokens` 表对旧代码完全透明（旧代码不读它），留在库里无任何影响。
3. **兜底开关**：只要 `DISABLE_RECEIVE_TOKEN` 未设置（默认未设），环境变量兜底始终启用——这是天然的安全网。回退前**不要**设置它。
4. **配置回退（v1.0.3）**：旧代码不读 `notify.*` / `retention_days` / `phone_area_*` 键，留着不影响旧版；如需彻底回到“纯环境变量”配置，删除这些键即可（`schema_meta` 与 `settings_rev` 保留不动）。删除后环境变量立即重新生效，无需重启。

> 检查清单：`RECEIVE_TOKEN` 仍在 → 旧代码可跑 → 回退安全。

## 六、常见问题

**Q：升级后 `/api/receive` 返回 403 了？**
与旧版状态码分布一致（鉴权失败一律 403）。检查：推送端 token 是否被改过；`DISABLE_RECEIVE_TOKEN` 是否误设为 `"true"`（设了就停用了环境变量兜底）。

**Q：旧库里的历史消息会丢吗？**
不会。自愈只增不改：建新表、补新列（带默认值）、建索引，不动任何现有数据。

**Q：多个实例/多副本会冲突吗？**
自愈语句全部幂等，并发首请求对「重复补列」有专门容错（`duplicate column` 视为成功）。

**Q：v1.0.3 之后，我没在设置页配置通知，原来的环境变量会失效吗？**
不会。数据库里没有对应键时继续读旧环境变量；只有你在设置页保存（或点「从环境变量导入」）后，数据库值才优先。敏感字段留空保存不会清空已有值，必须勾选「清除」才会移除，并同时遮蔽同名环境变量。

**Q：两个管理员同时改设置会怎样？**
设置页带修订号保存：后保存的一方会收到「设置已被其他会话修改」，整批不写入，重新打开页面再保存即可；不会出现半套配置。
